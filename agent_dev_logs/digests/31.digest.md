# 📓 Digest — [\#31](https://github.com/ufal/atrium-alto-postprocess/issues/31) `open`: Adaptation to othet than ALTO.XML inputs with text

**Labels**: `development`, `integration`
**Status**: 🟡 Planned — opened 2026-07-24, no comments yet; design work done offline (this session) and
captured in [`../plans/31.plan.md`](../plans/31.plan.md). No production code changed.

## 🎯 Goal & Core Constraint
Adapt the pipeline to digest any text-containing OCR-engine output — not just ALTO XML — into
ordered plain text (`<format>-2-txt`), per the issue body. The JSON half of this already exists
(`extract_JSON_2_TXT.py`'s schema-agnostic `TARGET_KEYS` leaf-walk) but rests on an unstated
one-file-one-page assumption that doesn't hold for every OCR engine.

## 🏆 Headline Findings & Conclusions

**1. The gap is narrower than the issue title suggests.**
Text extraction from generic JSON already works end-to-end (`extract_JSON_2_TXT.py`,
`json_stats_create.py`, `run_pipeline.py --method json-keys`) — undocumented in `README.md`, but
functional. What's missing is page splitting specifically, and it's already tagged with the exact
gap in three places in the live code: `run_pipeline.py`'s `INPUT_FORMATS["json"]["split_script"] =
None` comment is tagged `(#31)` directly, and `json_stats_create.py`'s docstring states outright
that the pipeline's page model for JSON is "one file = one page."

**2. Real OCR/Doc-AI engines don't agree on how to represent multi-page documents.**
Researched Azure Document Intelligence, AWS Textract, docTR, pero-ocr, OCR.space. Two structural
families dominate: a nested "pages" array (Azure, docTR, most PDF-text-layer dumps) vs. a flat
element list tagged with a per-item page field (AWS Textract). pero-ocr — the Brno/DCGM tool most
relevant to this project's Czech historical-document domain — already emits one file per page,
which validates rather than invalidates the pipeline's current default.

**3. No real sample JSON exists to design against.**
Confirmed with K4TEL: no concrete OCR engine/sample is driving this yet, so the design stays
deliberately generic — detect the two known structural families heuristically, fall back to
today's single-page behaviour — rather than hardcoding to one vendor's schema.

**4. Design settled, captured in `31.plan.md`.**
Page splitting unifies into `page_split.py` itself (additive `split_json_document()`, dispatched
by file extension; `split_alto_xml()` untouched) rather than a parallel script. The output
convention mirrors ALTO exactly (`<base>-<page>.json`, same directory shape) — which usefully means
`json_stats_create.py`'s existing "scan root + one level of subdirectories" walk needs only a small
targeted fix (derive `file`/`page` from the split filename the same way `alto_stats_create.py`
already does) rather than a rewrite.

## 🏁 Final Bottom Line
Planning-only so far — no code has changed. `agent_dev_logs/plans/31.plan.md` holds the full design
(detection whitelists, algorithm sketch, file-by-file change list, risks, verification criteria)
and is ready to implement against. Two things flagged for whenever implementation starts: the two
`test_run_pipeline.py` cases that currently assert JSON has no split stage will need to flip, and a
`--force-single-page` escape hatch was deferred out of the plan but should probably land alongside
the main change.
